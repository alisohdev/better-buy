# Scan retention and administration

User scan history retains the latest three terminal scans for each user/location/provider, for a rolling 24 hours measured from collection start (creation when no start exists). Queued/running scans are preserved. User-facing result endpoints return SCAN_EXPIRED (410) after 24 hours, even before physical cleanup. History queries enforce retention independently of cleanup timing. Cart items remain, but pricing requires a fresh successful scan. Frontend freshness timers hide cached offers and old notification prices without claiming a campaign has ended.

The existing maintenance goroutine performs small cleanup batches every 30 seconds: 100 raw response/contribution rows per table, one obsolete scan, 100 expired shared-cache entries, and 100 expired diagnostics/audit rows. No new daemon or payload loading is introduced. Completed normalized deals are separate from raw resumable responses. Raw checkpoints for active jobs remain intact. Results and projections cascade on scan deletion; deals are explicitly deleted because the legacy table has no scan foreign key.

Scan diagnostics retain only owner/scan IDs, provider, status, error code, timestamps and counts for 72 hours. They deliberately have no scan foreign key so errors survive result pruning. No provider headers, tokens, raw response bodies, password data or customer coordinates are exposed. Operational journald retention is three days with a 100 MB limit.

ADMIN_PHONES in the protected backend environment contains the normalized verified admin phone. Admin access requires a real authenticated session, phone verification and allowlist membership. Destructive operations also recheck the admin account password, require the exact DELETE SCANS confirmation, check request origin and leave a three-day audit record. Session ownership is never switched.

GET /api/admin/scans?userId=&page=1 lists 100 scan metadata rows. GET /api/admin/scan-logs?userId=&scanId=&page=1 lists at most 100 diagnostics from the last three days. GET /api/admin/scans/{id}/products?page=1 shows 50 recorded product rows. DELETE /api/admin/scans accepts {userId,scanId,password,confirmation}; empty selectors mean all scans. It queues deletion and returns 202 with queued count. Cleanup cancels active requested scans through the normal queue path and waits for worker ownership to end before removal. Users, addresses and saved shopping/wishlist entries are not deleted.

The admin UI provides a global scan manager and a per-user view, with paginated scan/results/error inspection and reviewed deletion scope. A deployment applies migration 0025 before enabling the new backend. The one-off `cmd/retention` runs bounded batches for the initial backlog. SQLite VACUUM is an operator task after cleanup with the API paused; it is not run by the periodic scheduler. Keep one rollback release and one completed database backup.
