# Snapp Market acquisition feasibility audit

## Decision

**PIVOT.** Use Okala as the primary provider for a narrower grocery deals product. Treat Digikala Fresh as supplementary while validating its repeatability and coverage. Keep Snapp Market out of any promise of fresh automatic results. The production journal confirms intermittent historical success followed by consistent rejection in the current retained scan sample.

## Hypotheses and confidence

- **Source network or different edge behavior is the leading explanation.** The same token POST succeeds locally and fails on the VPS. Both resolve the same addresses but connect to different peers, so source IP, hosting prefix or ASN, geography, route, edge policy and origin behavior are not isolated. RIPE RIS reported the VPS address in 37.152.176.0/21 (AS202468), and the two destination addresses in AS205585. Routing ASN is not an IP reputation measurement and does not establish a provider blocklist. [RIPEstat network info](https://stat.ripe.net/docs/data-api/api-endpoints/network-info)
- **CDN versus application enforcement is unresolved.** Both successful and rejected responses carry the ArvanCloud header. The HTML error and normal storefront title differ from successful JSON but cannot distinguish an edge rule, an origin policy, or an error page rewrite. Provider-side logs keyed by the correlation ID would be needed.
- **DNS, certificate verification, and HTTP/1.1 do not explain the reproduced failure.** Both reached the service over valid TLS and received HTTP responses. Neither resolve path produced a usable AAAA address. HTTP/2 and independent IPv6 connectivity were not verified. The rejection reproduces independently of Go and with no redirect.
- **An obsolete token or base catalogue request is unlikely to explain this failure.** The local token and authenticated Market Party results match the collector's expected payload shapes. A full campaign scan and all discovery contracts were not verified. Longer term endpoint drift is still possible.
- **Rate limits or an IP reputation rule remain possible.** The observed failure is 403, with no Retry-After or X-RateLimit-Limit. A long-duration policy can still return 403. No higher-rate traffic, proxy, route overrides, or alternate egress tests were used, and no provider rule or reputation score was verified.

## Collector review

Public source review did not identify a first-party Snapp Market catalogue API contract or numeric guest quota for third-party automation. The [official API Responder repository](https://github.com/snappmarket/api-responder/blob/master/README.md) documents a Laravel utility. Private access policies may exist, and some provider website content was inaccessible during the review.

ArvanCloud documents HTTP 429 as the standard response when a configured request threshold is exceeded, and HTTP 403 for a firewall deny action. That weakens ordinary rate limiting as an explanation for this particular 403, while leaving custom security policy and origin enforcement unresolved. Firewall rules can inspect the source IP, ASN, country, and request attributes. ArvanCloud also documents customizable error pages and uses `X-Request-Id` for request tracing. These are CDN capabilities, with no evidence of Snapp Market's specific configuration. [Rate limiting](https://docs.arvancloud.ir/fa/cdn/security/rate-limit/) · [Firewall settings](https://docs.arvancloud.ir/fa/cdn/security/firewall/) · [Custom error pages](https://docs.arvancloud.ir/fa/cdn/custom-pages/) · [CDN headers](https://docs.arvancloud.ir/fa/cdn/headers/)

The Go collector acquires a guest token before an uncached provider read, tracks expiry using the advertised duration, and obtains another token when the current one expires. A protected read returning 401 can claim one refresh per scan and retry once. A request returning 403 exits with `UPSTREAM_FORBIDDEN` before that refresh logic. The independent VPS probe reproduces a 403 at token acquisition. All 12 retained failed scans have exactly one journal reservation, for the guest token POST, and no discovery responses or collected pages. See [transport and status handling](../apps/api/internal/providers/collect.go#L71), [token acquisition](../apps/api/internal/providers/collect.go#L349), and [session lifecycle](../apps/api/internal/providers/collect.go#L383).

No collector defect is needed to explain the reproduced failure. A useful diagnostic improvement would be to record only the request stage, HTTP status, response content type and upstream correlation ID. Keep tokens, raw requests, user locations and upstream bodies out of logs. Keep 403 non-retryable for an individual scan and avoid repeatedly scheduling a persistently rejected provider.

## Technical follow-up

### Confirmed

**Production stopped at the first request.** For the captured scan, the sole reservation was at `2026-11-24T07:09:34.238482309Z` and the scan finished at `07:09:34.248771804Z`. The operation was `POST https://svc.snapp.market/oauth2/default/token` with the query omitted here. The retained journal code is `UPSTREAM_FORBIDDEN`. Both Snapp token and data calls pass `allow401=true`; the collector handles 401 separately, so that operation plus the error code identifies 403 for this scan. The other 11 retained failures have the same one-reservation, zero-page shape. The original header and body were not stored. The separate VPS reproduction in the preceding comparison supplies the raw 403, content type, header classification and correlation ID. Do not attribute that probe's request ID to the production scan. The successful JSON response cache contains no rejected response. No new Snapp Market requests were made from the VPS in this follow-up.

**Normal request construction and HTTP client.** A shared Go client has an 8-second timeout and uses the standard transport, which pools connections, negotiates HTTP/2 when available and honors environment proxy configuration by default. The request helper reads then closes bodies. The Snapp path uses standard redirect handling, without the explicit same-host validation used by another provider path. A followed redirect is not separately journaled. The 8 MiB reader silently truncates oversized responses; it neither detects overflow explicitly nor drains the remainder for HTTP/1.1 connection reuse. Go's default response handling was sufficient to get a token and crawl base and discovery pages locally.

**Request volume, caching and concurrency.** A cold enriched scan normally pays for token issuance, Market Party pages, nearby-store list pages, a home request per candidate code, a category request per eligible store and a page-zero probe per distinct campaign candidate. It then fetches the remaining campaign pages, including the empty terminal check when the listing is nonempty, plus any uncached title lookup. Page-zero probes and prefetched pages are read again from the scan journal during the ordered merge, so those logical rereads normally do not produce new HTTP traffic. There is no cross-scan Snapp response sharing or process-wide Snapp throttle in the adapter. Discovery runs serially. Campaign enrichment can start batches of up to 24 reads per scan. It prefetches against a reported count before validating the earlier pages, so count drift or an early terminal/error page can leave speculative calls unused. Request totals depend on location, discovered scopes, pages, and failures. The five successful November 16–17 snapshots used **54–97 journal reservations**, took **10.2–35.8 seconds** and closed **14–15 campaign units** plus Market Party. Three expanded scans failed after **1,089–2,090 reservations**. Reservations are logical transport attempts and need not equal on-wire requests when redirects or transparent transport retries occur. The current journal limits each operation to three reservations but has no whole-scan Snapp request ceiling. [Request and cache paths](../apps/api/internal/providers/collect.go#L67) · [Discovery](../apps/api/internal/providers/campaigns.go#L213) · [Prefetch](../apps/api/internal/providers/campaigns.go#L575) · [Reservation accounting](../apps/api/internal/providers/journal.go#L117)

**Retries, token ownership, and cancellation.** Token POST uses one attempt per invocation. GETs can retry network failures, 408, read errors and 5xx up to three times with 1- and 2-second waits. A 429 can retry inline if the parsed wait is at most five seconds; a terminal 429 remains queue-retryable, and the queue waits only one or two seconds before requeuing, so longer upstream delays are not preserved across layers. Operation caps limit repetitions of the exact same path/query but do not coordinate a cooldown across concurrent operations or scans. 403 is terminal for the scan; new wishlist jobs are a separate source of repeated token calls. Each campaign prefetch worker copies the current guest state. On expiration this can trigger parallel token acquisitions, and on 401 the persistent refresh claim prevents multiple refresh winners but does not share the replacement token with siblings. A sibling can terminate the batch despite a successful refresh. This is a code-level defect under expiry or 401, with no evidence it triggered the first-request production rejection. HTTP and SQL operations use cancellable contexts, backoffs are cancellable, and the queue polls cancellation/heartbeat at 500 ms. In-flight requests already sent cannot be undone. [Transport retries](../apps/api/internal/providers/collect.go#L71) · [Guest renewal](../apps/api/internal/providers/collect.go#L383) · [Queue retry](../apps/api/internal/scans/queue.go#L883)

**Pagination and completeness.** Market Party decodes into a non-pointer count; a missing count and vendor list can be interpreted as an empty complete result if the top-level status is true. Each page replaces the total, and the repeat check uses vendor order. Discovery counts vendor rows before deduping codes and requires the advertised total to stay fixed. Partial page overlap can inflate the count, and count drift can fail a scan. Some malformed/unsupported store and campaign candidates are silently skipped, so complete coverage can describe the accepted manifest while omitting candidates. Campaign completion checks the empty terminal page, raw row count and repeated page fingerprints and marks bounded drift or quarantines incomplete, but cannot prove every provider offer was discovered. These are implementation and coverage limitations independent of the token rejection. [Market Party pagination](../apps/api/internal/providers/collect.go#L178) · [Campaign discovery](../apps/api/internal/providers/campaigns.go#L213) · [Campaign pagination](../apps/api/internal/providers/campaigns.go#L601)

### Probable

- The production refusal is related to the source network, selected CDN edge, or origin policy, with different connected peers still a confound. A Go request-construction defect is unlikely given the independent HTTP/1.1 reproduction and the successful local Go HTTP/2 scan stages.
- Okala has sufficient evidence to justify a pilot as a standalone deal discovery product in covered areas. Its incomplete scans and high cold-scan work mean reliability and freshness should be measured by location before promising full coverage. One retailer cannot support a cross-retailer comparison claim.

### Unverified

- The specific IP, ASN, geography, reputation or edge rule, and whether the decision came from ArvanCloud or the application. No VPS HTTP/2 probe was added after the refusal. IPv6 connectivity and edge equivalence remain unverified.
- Local full campaign reach, final unique product and offer totals, exact current full-scan request cost, and repeat scheduled Snapp Market success. The bounded run stopped at 120 requests before campaign enrichment.
- Okala performance across all target locations and schedule slots. Digikala Fresh repeatability, coverage outside the observed case, and suitability for scheduled alerts.

### Disproven

- The rejection requires high concurrency, an expiring guest token, renewal, or pagination activity within the failed scan. Production failed on its initial token POST; the independent single-request probe reproduced it.
- The VPS was continuously blocked from the first retained rejection onward. The diagnostic table shows two later successes before the current run of failures.
- Guest authentication proves complete collection. It succeeded locally, but the controlled scan could not finish campaign discovery within the cap.

### Decision gate

**PIVOT to an Okala-first product.** Track scheduled completion, coverage flags, catalogue freshness and request volume across representative locations before expanding the promise. Keep Digikala Fresh supplementary pending repeat success. Reconsider Snapp Market only after stable permitted access, terminal validation for both feed groups, and bounded request costs on repeated scheduled runs. No deployment, production code or database changes were made.
